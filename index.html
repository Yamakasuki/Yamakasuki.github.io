API do grafo de conhecimento

Knowledge graph API

Um grafo de conhecimento é um mapa de fatos ligados entre si, do qual o sistema tira conclusões. Ajudei a desenhar esse mapa e tive papel principal na API que entrega essas conclusões para outros sistemas.

A knowledge graph is a map of connected facts from which a system draws conclusions. I helped design that map and played a lead role in the API that delivers those conclusions to other systems.

Como eu fiz

How I did it

  1. Participei da modelagem desde a ideia: quais entidades, relações e regras o sistema precisa ter.
  2. O grafo vive no RDFox, que aplica regras de inferência e gera fatos novos a partir dos que já existem.
  3. Criei endpoints REST em Python (FastAPI) que expõem o grafo como um microsserviço.
  4. Um LLM consome a API para gerar recomendações personalizadas, e um chatbot a usa para conversar com as pessoas.
  1. I took part in the modeling from day one: which entities, relations and rules the system needs.
  2. The graph lives in RDFox, which applies inference rules and derives new facts from existing ones.
  3. I built REST endpoints in Python (FastAPI) that expose the graph as a microservice.
  4. An LLM consumes the API to generate personalized recommendations, and a chatbot uses it to talk to people.

Resultado: o LLM e o chatbot usam a mesma fonte de verdade, e cada recomendação pode ser rastreada até um fato ou uma regra. Isso deixa menos espaço para a IA inventar respostas — essencial em saúde.

Result: the LLM and the chatbot share a single source of truth, and every recommendation can be traced back to a fact or a rule. That leaves less room for the AI to make things up — essential in health.

TRIA: agentes de IA seguros com LLM local

TRIA: secure AI agents with a local LLM

Como deixar um assistente de IA executar tarefas no computador sem abrir uma porta para ataques — e sem mandar seus dados para a nuvem.

How to let an AI assistant run tasks on a computer without opening a door to attackers — and without sending your data to the cloud.

O problema

The problem

Agentes de IA não só respondem: eles executam comandos e mexem em arquivos. Quando dependem de uma API na nuvem, expõem dados a terceiros e param quando a cota acaba — aconteceu no meu protótipo, que travou com um erro 429 de cota esgotada.

AI agents don't just answer — they run commands and touch files. When they depend on a cloud API, they expose data to third parties and stop when the quota runs out — it happened to my prototype, which halted with a 429 quota-exhausted error.

Como eu fiz

How I did it

  1. Desenhei uma arquitetura com três camadas de defesa, cada uma verificável em separado.
  2. Rede: nada fica exposto na internet; o acesso remoto passa por uma VPN zero-trust (WireGuard, via Tailscale).
  3. Controle: um gateway que só escuta na própria máquina (loopback) e exige token concentra autenticação e sessões.
  4. Inteligência: o modelo roda localmente com Ollama, então o contexto não sai da máquina.
  5. Implementei um protótipo com três agentes — cada um com bot no Telegram, área de trabalho e credenciais próprias — e o testei numa VM isolada (VMware) e no WSL2 com GPU.
  1. I designed an architecture with three layers of defense, each one verifiable on its own.
  2. Network: nothing is exposed to the internet; remote access goes through a zero-trust VPN (WireGuard, via Tailscale).
  3. Control: a gateway that only listens on the machine itself (loopback) and requires a token handles authentication and sessions.
  4. Intelligence: the model runs locally with Ollama, so the context never leaves the machine.
  5. I implemented a prototype with three agents — each with its own Telegram bot, workspace and credentials — and tested it on an isolated VM (VMware) and on WSL2 with a GPU.

O que descobri: numa RTX 3060, modelos de 7 a 9 bilhões de parâmetros geraram de 50,8 a 71,5 tokens por segundo — mas o mesmo mecanismo que dá essa potência enfraquece o isolamento: o gateway ficou alcançável a partir do Windows, e os discos dele, acessíveis ao agente. Já a VM isolada, com 4 GiB de memória, não comporta nenhum dos modelos. Ou seja: no hardware avaliado, isolamento forte empurra a IA para fora da máquina — um trade-off que precisa ser escolhido de forma consciente.

What I found: on an RTX 3060, 7–9 billion-parameter models generated 50.8 to 71.5 tokens per second — but the same mechanism that provides that power weakens isolation: the gateway was reachable from Windows, and its drives were accessible to the agent. The isolated VM, with 4 GiB of memory, can't fit any of the models. In short: on the hardware evaluated, strong isolation pushes AI off the machine — a trade-off that has to be made consciously.

Medidor inteligente de vazão de água

Smart water flow monitor

Um medidor que mostra, em tempo real e de qualquer lugar, quanta água está passando pelo cano — e avisa quando algo parece vazamento.

A meter that shows, in real time and from anywhere, how much water is flowing through a pipe — and warns when something looks like a leak.

O problema

The problem

O hidrômetro comum é lido uma vez por mês, então um vazamento pode passar semanas sem ninguém perceber.

A regular water meter is read once a month, so a leak can go unnoticed for weeks.

Como fizemos

How we built it

  1. Sensor: um YF-S201 (efeito Hall) gera um pulso elétrico a cada volta do rotor movido pela água.
  2. Placa: um Heltec WiFi LoRa 32 (ESP32) conta os pulsos e calcula a vazão em L/min e o volume acumulado.
  3. Nuvem: os dados vão por Wi-Fi para o ThingsBoard Cloud, que guarda a telemetria; também estudamos LoRa para longas distâncias.
  4. Painel: um dashboard web em Flask mostra vazão atual, média móvel, tendência (regressão linear), projeção de consumo em 24 h, alertas e um relatório gerado automaticamente.
  1. Sensor: a YF-S201 (Hall effect) sends an electrical pulse each time the water spins its rotor.
  2. Board: a Heltec WiFi LoRa 32 (ESP32) counts the pulses and computes the flow in L/min and the accumulated volume.
  3. Cloud: the data travels over Wi-Fi to ThingsBoard Cloud, which stores the telemetry; we also studied LoRa for long distances.
  4. Dashboard: a Flask web dashboard shows current flow, moving average, trend (linear regression), a 24-hour consumption forecast, alerts and an auto-generated report.

Resultado: sistema funcionando de ponta a ponta, do sensor ao painel. Próximo passo em estudo: detectar ar na tubulação, que faz hidrômetros cobrarem por água que não passou.

Result: an end-to-end working system, from sensor to dashboard. Next step under study: detecting air in the pipes, which makes meters charge for water that never flowed.

Compilador MicroC, etapa por etapa

MicroC compiler, stage by stage

Um compilador escrito em Python para a MicroC, uma linguagem parecida com C: ele lê o código, entende a estrutura e aponta cada erro com linha e coluna.

A compiler written in Python for MicroC, a C-like language: it reads the code, understands its structure and points out every error with line and column.

O desafio

The challenge

Construir as fases de um compilador de verdade a partir de uma especificação formal, com testes automáticos conferindo cada entrega.

Build the phases of a real compiler from a formal specification, with automated tests checking every delivery.

Como eu fiz

How I did it

  1. Análise léxica: um autômato dirigido por tabela quebra o código em tokens (palavras, números, símbolos), cada um com sua posição exata.
  2. Gramática LL(1): remoção da recursão à esquerda e cálculo dos conjuntos FIRST, FOLLOW e START, para que a gramática possa ser lida sem voltar atrás.
  3. Análise sintática: um parser por descida recursiva, com uma função por regra da gramática, monta a árvore sintática (AST).
  4. Análise semântica: resolução de nomes, escopos, tabela de símbolos e verificação de tipos, com mensagens de erro claras.
  1. Lexical analysis: a table-driven automaton splits the code into tokens (words, numbers, symbols), each with its exact position.
  2. LL(1) grammar: left-recursion removal and FIRST, FOLLOW and START set computation, so the grammar can be parsed without backtracking.
  3. Parsing: a recursive-descent parser, with one function per grammar rule, builds the abstract syntax tree (AST).
  4. Semantic analysis: name resolution, scopes, a symbol table and type checking, with clear error messages.

Resultado: as quatro etapas entregues passam em 88 testes automatizados (pytest). Próxima etapa: análise de fluxo de controle.

Result: the four delivered stages pass 88 automated tests (pytest). Next stage: control-flow analysis.

Feito sobre o código-base da disciplina, que define as interfaces e os testes.

Built on the course's starter code, which defines the interfaces and tests.

API de Machine Learning em contêineres

Containerized Machine Learning API

Peguei uma aplicação de IA que rodava em três máquinas virtuais e a transformei em contêineres que sobem com um único comando.

I took an AI application that ran on three virtual machines and turned it into containers that start with a single command.

O problema

The problem

O ambiente original usava três VMs Vagrant (aplicação, banco e proxy) montadas por scripts de shell — pesado e difícil de reproduzir em outra máquina.

The original environment used three Vagrant VMs (app, database and proxy) set up by shell scripts — heavy and hard to reproduce on another machine.

Como eu fiz

How I did it

  1. Empacotei a API Flask, que serve uma rede neural (MLP), numa imagem Docker.
  2. Orquestrei a aplicação com Docker Compose, com o nginx como proxy reverso na frente.
  3. Criei uma pipeline de CI no GitHub Actions que sobe os contêineres e executa testes unitários (as funções da rede) e de integração (chamadas reais à API).
  4. Gerei um modelo de teste leve para a CI não depender do arquivo pesado do modelo.
  1. I packaged the Flask API, which serves a neural network (MLP), into a Docker image.
  2. I orchestrated it with Docker Compose, with nginx as a reverse proxy in front.
  3. I created a CI pipeline on GitHub Actions that brings up the containers and runs unit tests (the network's functions) and integration tests (real API calls).
  4. I generated a lightweight test model so CI doesn't depend on the heavy model file.

Resultado: três VMs viraram dois contêineres que sobem com docker compose up, com testes prontos para rodar a cada push.

Result: three VMs became two containers that start with docker compose up, with tests ready to run on every push.

Partiu do projeto de um colega; minha contribuição foi a migração para contêineres e a CI.

It started from a classmate's project; my contribution was the move to containers and the CI.
